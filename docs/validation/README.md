# Воспроизводимая валидация PlayFit Vision

Протокол `playfit-validation-v1`, правила `provisional-side-v1`, 20 октября 2026.
Инструменты реализованы. Реальные записи и эталонная разметка в проекте отсутствуют: размер реального набора **0 видео, 0 людей, 0 попыток**. Измерений точности на людях нет. Текущий [отчёт](REPORT.md) явно разделяет проверки вычислений и внешнюю валидацию.

## Локальный запуск

Нужны установленные зависимости (`npm ci` при первом запуске), Chrome/Edge с `requestVideoFrameCallback`, локальная копия модели и WASM из `public/`. Интернет во время прогона не нужен. Vite обслуживает статические файлы на loopback; прикладного сервера и загрузки записей во внешние сервисы нет. Не переносите записи в `public/`: эта папка публикуется со сборкой.

1. Создайте игнорируемую `validation-private/`; положите туда видео, документы разрешения, JSON-разметку и будущие выгрузки. Исходные имена и пути файлов не попадают в экспорт. Связь анонимного ID с человеком храните отдельно и локально. Не используйте случайные интернет-видео без проверки прав.
2. Запустите `npm run dev`, откройте `http://127.0.0.1:5173/validation.html`. Для сборки: `npm run build`, затем `npm run preview` и `/validation.html` по адресу preview.
3. Выберите локальное видео и нажмите «Получить SHA-256 и длительность». Создайте JSON по [формату](format.md). Скопируйте `video.sha256` и точную длительность из страницы; не подставляйте хеш примера. Видео должно иметь конечную длительность и декодироваться браузером. Если контейнер не содержит длительность, подготовьте локальную копию с корректным индексом и разметьте именно её.
4. Разметчик просматривает исходное видео независимо от вывода анализатора по [памятке](annotator.md). Нужны время исходного файла от нуля, вариант, исходы, все критерии и неопределённость. Запишите ручные подтверждения ракурса заранее; не подбирайте их по контрольным результатам.
5. Выберите JSON, интервал выборки (по умолчанию 50 мс) и нажмите «Прогнать MediaPipe и сравнить». Оставьте вкладку видимой. Последовательные seek не являются перемотками тренировочной сессии: анализатор получает возрастающие **абсолютные таймкоды исходного файла**; MediaPipe — те же монотонные таймкоды. Настенное время обработки не влияет на сглаживание.
6. Сохраните `clip-id.run.json` и `clip-id.report.json` в `validation-private/`. В браузере папка загрузки определяется настройками пользователя; перенесите файлы из Downloads перед дальнейшей работой. Сырые точки и кадры не экспортируются; выгрузка всё равно считается частным материалом. Хеш видео также позволяет связать копии записи.
7. Повторите сравнение готового `.run.json` на странице или из терминала:

```powershell
npm run validation:report -- validation-private/clip.annotation.json validation-private/clip.run.json validation-private/clip.report-2.json
```

CLI собирает только модуль метрик через существующий Vite в игнорируемую `.validation-build/`. Он не запускает модель, не требует браузера, не перезаписывает существующие файлы и пишет отчёт только внутрь `validation-private/`. Несовпадение хеша, длительности, упражнения, варианта, подтверждений или версий приводит к ошибке. Сначала сохраняйте эталон и сырую выгрузку; итоговый отчёт можно пересоздать.

Пример **только арифметики метрик**, без видео и MediaPipe:

```powershell
npm run validation:report -- docs/validation/examples/synthetic.annotation.json docs/validation/examples/synthetic.run.json validation-private/synthetic.report.json
npm run validation:test
npm test
npm run build
```

Для повторного CLI-прогона выберите новое имя выходного файла. [Ожидаемый JSON](examples/synthetic.report.json) доступен для сравнения. Его времена производительности вымышлены и не являются бенчмарком. Нулевой хеш в примере — явная заглушка, а не хеш видео.

Для воспроизведения технического прогона **реального MediaPipe на искусственном пустом видео**:

```powershell
npm run validation:fixture
```

Команда без дополнительных зависимостей создаёт `validation-private/synthetic-blank.webm` (2 с, 320×240, VP8, 10 кадров/с) и соответствующий JSON. Существующие файлы не перезаписывает. Выберите их на странице и оставьте интервал 50 мс. Ожидаются 20 уникальных кадров, 21 повторный таймкод сетки, ноль попыток, нулевое достаточное покрытие и `evidence: synthetic-only`. Это проверяет декодирование, локальные модель/WASM, экспорт и отсутствие ложного счёта на одном пустом ролике. Это не качество распознавания движений людей; скорости такого прогона не обобщаются на тренировку.

## Что именно проверяется

- `src/exercises/analyzer.test.ts`: искусственные точки → анализатор; это отдельный слой, без MediaPipe и декодирования.
- `src/validation/*.test.ts`: искусственные события/наблюдения → вычисления метрик и сбор выгрузок. Пустые наборы, неоднозначные сопоставления, пропуски, FP/FN, неопределённость и интервалы исключения.
- Страница валидации: локальный файл → декодированные кадры → **реальный** `PoseLandmarker` → тот же `createAnalyzer` → выгрузка → сравнение с независимой разметкой. Результаты этого слоя на реальных материалах пока отсутствуют.
- Тренировочный интерфейс, воспроизведение в реальном времени, камера, голос, pause/seek/restart и портретный overlay требуют отдельной ручной проверки. Offline seek-прогон не подтверждает их работу и не является тестом достижимого FPS камеры.

Модель создаётся общей с приложением фабрикой: GPU с текущими confidence-порогами, при ошибке CPU с исходными библиотечными defaults. Делегат и фактически заданные настройки записываются; сравнивать GPU и CPU как один режим нельзя. Каждый прогон создаёт новый детектор и анализатор, вызывает `finish(durationMs)` один раз и закрывает детектор.

Выборка использует `requestVideoFrameCallback.mediaTime`, а не запрошенный `currentTime`: одинаковые декодированные таймкоды пропускаются и учитываются как `duplicateFrames`. Получаем не каждый кадр исходника, а сетку с указанным интервалом; VFR, короткие события и декодер могут менять покрытие. Ошибки детектора передаются анализатору как пустые наблюдения с `detector_error`. Ошибки чтения/seek останавливают прогон, а не превращаются в успешный отчёт.

Метаданные содержат SHA-256 видео, модели, всех локальных JS/WASM-вариантов, конфигурации и объединённых исходников анализатора/геометрии/детектора/runner; версии пакета и MediaPipe берутся из lockfile. Зафиксированы параметры правил, выборка, размеры, делегат и характеристики браузера. Для повторения также сохраните Git commit (`git rev-parse HEAD`) рядом с набором. GPU, браузер и декодер могут давать различия: воспроизводимость означает фиксированный протокол и прослеживаемую среду, не обещание побитового равенства.

## Метрики и сопоставление

Все времена — миллисекунды исходного файла, интервалы полуоткрытые `[startMs, endMs)`. Обе границы попытки должны отличаться от эталона не больше чем на **1000 мс**, и интервалы должны пересекаться на положительную длительность. Попытки упорядочены; алгоритм динамического программирования находит максимальное число пар с сохранением временного порядка, затем минимизирует сумму абсолютных ошибок обеих границ. При равенстве выбирается детерминированный переход match. Каждое событие участвует максимум в одной паре; исходы и замечания не влияют на выбор пары. Допуски предварительные: фиксируйте до просмотра контроля. Программный API допускает другие допуски; они записываются в отчёт. Размер одного сравнения ограничен 4 млн ячеек DP — длинные записи разделяйте заранее.

Любая попытка, пересекающая `unassessable`, целиком исключается из сопоставления и счёта; её ID остаётся в отчёте. Это консервативное правило может исключить значительную часть сложных движений: всегда публикуйте исключённые длительности и число событий. Критериальная неопределённость внутри оценимой попытки задаётся статусом `unassessed`, без глобального исключения.

| Поле отчёта | Смысл |
| --- | --- |
| `count` | Число полных повторов эталона/алгоритма; signed error = prediction − reference; absolute error; число попыток, пропуски/лишние; матрица исходов matched-пар |
| `criteria[code]` | На попытку максимум одно замечание по критерию: TP, FP, FN, TN, abstention, игнорируемая эталонная неопределённость |
| `criteria[code].precision/recall` | TP/(TP+FP), TP/(TP+FN); при нулевом знаменателе `null` |
| `timing` | Ошибки начала/конца и время первого появления итоговой записи минус конец эталонной попытки, только для matched-пар |
| `criteria[code].latencyMs` | Время первого публичного feedback данного критерия (либо финального замечания при закрытии) минус `onsetMs` эталона; только TP с известными временами |
| `coverage` | Длительность достаточных данных, доступность каждого критерия, отдельно видимость точек, подготовка и ракурс |
| `performance` | Время инициализации, всего, декодирования+анализа, длительности inference/анализа, число кадров и дубликатов; отдельно от качества |

На matched-паре эталон `deviation` с прогнозом `passed`, `unassessed` или с пропущенной попыткой даёт FN. Эталон `passed` и прогноз `deviation` дают FP; оба `passed` дают TN. `unassessed` алгоритма учитывается дополнительно в `abstained`, не считается положительным результатом. Эталон `unassessed` игнорируется для данного критерия даже при замечании алгоритма. Каждое замечание в лишней попытке даёт FP. Отсутствующая отрицательная попытка записывается в `missingNegativeAttempt`, а не в TN. Пустое видео без событий не создаёт искусственных TN. Недостаточно одного суммарного count error: ошибки разных попыток могут взаимно компенсироваться.

Отрицательная задержка сохраняется: это раннее обнаружение/ошибка границ, её нельзя обнулять. Неизвестный onset не выводится из середины попытки — TP остаётся, задержка отсутствует и учитывается в `latencyUnavailable`. Пропущенные события не имеют измеренной задержки: читайте распределения только вместе с recall. Перцентили — nearest rank `ceil(p*N)`; пустые распределения имеют `count: 0` и `null`.

Покрытие — интеграл по времени, а не доля кадров. Наблюдение поддерживает интервал от своего таймкода до следующего, максимум `min(2 × sampleIntervalMs, 700)` мс; оставшаяся часть разрыва и время до первого кадра считаются непокрытыми. Последний кадр поддерживает хвост до длительности с тем же ограничением. Объединённые `unassessable` исключены из числителя и знаменателя. При нулевой оценимой длительности fraction = `null`. `sufficient` требует `observation.ready` и публичного угла, то есть учитывает блокировку ракурса, но не требует завершённой подготовки. `preparedMs` отдельно считает ready/active. Доступность критериев берётся из текущих причин нехватки точек/ракурса, не из накопленного исхода попытки. `viewMs` сравнивайте с фиксированной категорией ракурса разметчика; покадровой разметки ориентации в v1 нет.

### Задержка после этапа 4

Экспорт сохраняет кандидатов `analysis.feedback` анализатора. Новая политика интерфейса `phase-cues-v1` дополнительно выбирает и подтверждает актуальное сообщение; её задержка показа/речи не измеряется этими полями. Прежнюю `latencyMs` нельзя объявлять задержкой доставленной человеку подсказки. Биомеханические правила и события анализатора не менялись. [Подробности и незавершённая проверка интерфейса](../actionable-feedback.md).

## Как провести настоящие измерения

Нужны разрешённые локальные записи, независимая разметка тренером, спорные случаи с adjudication, замороженные группы настройки/контроля и повторяемая среда. Подробный [план записей](recording-plan.md) задаёт разнообразие, разделение по людям и состав будущего отчёта. Пороговые правила остаются **предварительными и не проверенными специалистом**, пока соответствующая проверка не выполнена. Отсутствие замечаний не подтверждает безопасность упражнения.
