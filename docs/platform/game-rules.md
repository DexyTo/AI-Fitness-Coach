# XP, уровни и достижения — этап 5

Правила `progression-v1` определены только на сервере в `server/progression.ts`. Общие DTO и тексты причин — `shared/progression.ts`. Это учебный учёт структурированных результатов: сервер проверяет владельца, связь с запуском, снимок цели и согласованность результата, но не доказывает подлинность движений и точность компьютерного зрения. Видео и координаты остаются в браузере.

## Политика

- **20 XP за задание**, независимо от числа шагов, подходов, скорости и повторов сверх цели. Программа — одно задание, дети отдельно не награждаются.
- **60 XP в день**, общая проектная зона **Europe/Kyiv**. Дневной остаток ограничивает награду: `min(20, max(0, 60 − XP за этот день))`. Дата определяется временем первого успешного серверного завершения, а не датой/длительностью результата клиента. Успешная повторная отправка на следующий день не переносит награду и не создаёт новое событие.
- Начало — уровень 1, XP 0. `level = floor(totalXp / 100) + 1`, `levelXp = totalXp % 100`, до следующего уровня `100 − levelXp`. XP суммируется только по журналу с `currency='xp'`.
- Только новый серверный запуск аккаунта с `reward_rules_version='progression-v1'`, `mode='camera'`, проверенным снимком и полностью выполненной целью. В каждом предусмотренном подходе должны быть `ended='completed'` и `result.reps >= goal.reps`. Для программы дополнительно `ended='completed'`, все шаги и их цели. Ручной конец подхода с недобором, отсутствие подходов, прерванная программа не подходят. Полные повторы, неполные/неоценённые попытки и замечания остаются раздельными; замечания не отменяют полный повтор и не являются общим «процентом безопасности».
- Гость, demo, video, исторический импорт и старые запуски не дают XP и прогресс достижений. Миграция не делает backfill: NULL версии у прежних запусков сохраняется. Повтор старого результата, импорт, повтор миграций/каталогового наполнения не создают наград.
- После дневного предела полностью выполненные допустимые задания продолжают давать **факты активности и прогресс значков**. Число зачтённых повторов для достижений ограничено целью каждого подхода; дополнительные повторы не ускоряют прогресс. Частично выполненные задания в эти показатели не входят.

## Шесть достижений

| ID | Условие | Награда |
| --- | --- | --- |
| first | 1 допустимое полностью выполненное задание | Значок «Первый шаг» |
| five | 5 заданий | Значок «В своём ритме» |
| ten | 10 заданий | Значок «Десятка» |
| days | Активность в 3 разных дня Europe/Kyiv, подряд не требуется | Значок «Возвращайся к движению» |
| reps | 100 полных повторов в пределах целей | Значок «Сотня движений» |
| variety | Приседания и отжимания в допустимых заданиях | Значок «Два движения» |

Каждый значок выдаётся один раз, **без бонусных XP**, валюты и соревновательных очков. Можно получить несколько значков за одно событие. Условия и фактический прогресс видны в обзоре/профиле. Пока нет зачтённых событий, показатели равны нулю; вымышленных серий и приглашений нет.

## БД и согласованность

Миграция `005_progression.sql` добавляет nullable `workout_runs.reward_rules_version` без изменения старых миграций/данных:

- `progression_events`: result_id (PK/FK), user_id, reason, eligible, reps в пределах цели, exercises_json, event_at UTC, project_day, rules_version. Фиксирует решение и для исключённых новых результатов; импорт не создаёт событие.
- `reward_ledger`: пользователь, `currency: xp | competition_points`, `source_type: workout | challenge | duel`, source_id, amount > 0, event_at UTC, project_day, rules_version. Уникальность `(user_id,currency,source_type,source_id)`. На этапе 5 записывается только workout/xp, source_id — серверный **ID результата**, не run ID и не ID ребёнка.
- `user_achievements`: PK(user_id,achievement_id), result_id FK на событие, earned_at UTC, rules_version. Привязка хранит, какое завершение впервые выдало значок.

Сохранение результата, события, XP, значков выполняется в одной **BEGIN IMMEDIATE** транзакции SQLite. Сначала под блокировкой проверяется существующий результат. Точное повторение возвращает прежние данные (200), первый результат — 201, изменение — 409. Ошибка любого INSERT откатывает всё; можно безопасно повторить. Уникальные ограничения сохраняют однократность и при нескольких соединениях. Изменение/удаление записей журналов и достижений запрещено SQL-триггерами; архивирование результата меняет только archived_at.

Архив скрывает запись из списка истории, последних тренировок и прежних сводных показателей истории профиля. **Накопленный XP, значки, активность и статистика допустимых заданий остаются**: скрытие не отменяет произошедшего события. Прямые детали владельцу доступны. Новый запуск использует текущую доступную программу, завершение — ранее принятый снимок; изменение/архив шаблона не меняет награду.

## API и UI

- `POST /api/runs` сохраняет версию правил сервером. Клиент не передаёт версию, время начисления, XP или очки.
- `POST /api/runs/:id/complete` — единственный публичный путь начисления на этапе 5. Ответ `{result}` дополнен `result.reward`: `{reason,xp,earnedAt,achievements:string[]}`. earnedAt — время решения, включая исключённый новый результат; у старого/импорта null. achievements — названия значков, впервые выданных этим результатом. При повторе возвращается тот же receipt, он не означает новую выдачу.
- `GET /api/history` и `/api/history/:id` возвращают тот же receipt. Причины: awarded, daily_limit, demo, video, incomplete, legacy, import. Тексты UI объясняют каждую; гость видит отдельное объяснение без серверной награды.
- `GET /api/me/progression` → `{progression}`: xp, level, levelXp, nextLevelXp (100), todayXp, dailyLimit, workoutXp, timeZone, stats `{workouts,reps,days,exercises}`, activity (7 календарных дат по возрастанию, включая сегодня, `{day:'YYYY-MM-DD',workouts}`), achievements `{id,title,description,target,progress,earnedAt,reward}`. Никаких награждающих записей при GET нет.
- `GET /api/me/overview` → `{progression,recent:AccountResult[]}` (до 3 последних нескрытых результатов по серверному времени). Избранное использует существующий `/api/me/favorites`.
- `/overview` — персональная страница после входа/регистрации: уровень, XP, активность, последние результаты, избранное, достижения и CTA тренировки. `/profile` сохраняет редактор аватара/никнейма и показатели истории, добавляет уровень и коллекцию. Нужен вход; приватные данные определяются сессией, query userId запрещён, ожидаемый аккаунт проверяется `x-playfit-user`.
- Есть загрузка/пустые состояния/ошибка с повтором. Награда отображается только после подтверждения сохранения. Блокирующих анимаций нет; существующий reduced-motion сохраняется. Незавершённые запуски после reload не восстанавливаются, UI это не обещает.

## Контракт для этапов 6–8

`appendReward(db, RewardEvent)` — внутренний серверный интерфейс: `{userId,currency,sourceType,sourceId,amount,eventAt,rulesVersion}`. Требует активную транзакцию, положительное целое amount; точный повтор источника не вставляет строку, конфликт величины/версии бросает ошибку. Вызывать в immediate-транзакции завершения соответствующего **проверенного сервером** события; функция сама не проверяет чужое владение, снимок, дедлайн или выполнение задания и не заменяет эти проверки. Публичного API «начислить XP/очки» нет.

Испытания/дуэли должны хранить собственный снимок принятого задания и новые связанные камерные runs. Следующий этап определит отдельные источники/правила, использует `competition_points` для очков, не смешивая их с XP. Если добавляются XP испытаний/дуэлей, они должны соблюдать общий дневной предел или явно новую документированную версию политики. Не выдавать повторно workout XP за дочерние шаги. Даты/дедлайны — серверное UTC, дни — общая `projectDay`, недели понедельник–воскресенье. Недели/рейтинги на этапе 5 не реализованы.
