# Аккаунты и история — этап 2

Расширение этапа 3: [программы, снимки и формат ProgramRecord v2](programs.md). Те же `/api/runs`, `/api/runs/:id/complete` и `/api/history` теперь поддерживают программы наряду с одиночными WorkoutRecord v1. В смешанном экспорте `records` содержит только v1, а программы находятся в `programs`; импорт v1 остаётся прежним. Профиль суммирует полные повторы из дочерних результатов, демо исключает из личных показателей.

Реализованы локальные аккаунты по логину/паролю, профиль, связанные запуски и серверные результаты. Гость использует прежний `playfit.workouts.v1`. Вошедший пользователь читает только серверную историю; автоматического переноса и скрытого перехода на localStorage при ошибках нет. Видео, кадры и поток координат не отправляются на API. В SQLite сохраняются структурированные итоги, наблюдения и параметры анализа. Точность распознавания на людях этим этапом не проверяется.

## Запуск и миграции

`npm install`, `npm run db:migrate`, `npm run dev`. Зависимости этапа 1 сохранены; дополнительные пакеты не требуются. `002_accounts.sql` добавляет `users`, `auth_sessions`, `workout_runs`, `workout_results`, индексы и ограничения владельцев. Миграция 001 не менялась. Повтор и перезапуск сохраняют пользователей, сессии и результаты. При старте миграции применяются автоматически. Резервная копия БД требует корректной работы с WAL (например, SQLite backup API), а не копирования только основного файла во время записи.

Чистая серверная сборка теперь находится в `.server-build/server/`, общие контракты — `.server-build/shared/`, чистые типы анализа — `.server-build/src/exercises/`. `npm run start:server` указывает на новый entrypoint; определение корня проекта учитывает исходный и собранный код. SQL по-прежнему читается из `server/migrations/`. `shared/workout.ts` и `shared/historyValidation.ts` — общие типы и проверка согласованности WorkoutRecord v1. Анализатор и MediaPipe сервером не импортируются.

## Вход

Логин: 3–32 ASCII-буквы/цифры/`_`, регистр не различается, сохранение в нижнем регистре. Пароль: 8–128 символов, без обрезки пробелов; асинхронный Node.js scrypt, N=65536, r=8, p=1, 64 байта ключа, случайная 16-байтовая соль для каждого пароля. Формат БД `scrypt-65536-8-1$salt$hash`. Сравнение через `timingSafeEqual`. Обоснование API: [Node.js crypto](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). Не более двух одновременных KDF и 30 попыток регистрации/входа с loopback-IP за 15 минут в процессе; после перезапуска лимит сбрасывается. Это локальная учебная эксплуатация, не инфраструктура публичного auth-сервиса.

Сессия: случайные 32 байта; в БД только SHA-256 токена, владелец и абсолютный UTC-срок 30 дней. Cookie `playfit_session`, `Path=/api`, `HttpOnly`, `SameSite=Strict`, `Max-Age=2592000`, без Domain и Secure для локального HTTP. Cookie недоступна React и не хранится в localStorage. Вход заменяет текущую сессию этого браузера, выход удаляет строку и cookie. Другие браузерные сессии пользователя сохраняются. Просроченная сессия не даёт доступа; очистка просроченных строк выполняется при новом входе.

Все изменяющие `/api/*` запросы требуют `X-PlayFit-Request: 1`. Дополнительно Origin, если присутствует, должен точно совпасть с протоколом/Host запроса; `Sec-Fetch-Site: cross-site` отклоняется. CORS не включён: сторонний JavaScript не получает разрешение на custom header, HTML-форма его не выставляет. Proxy Vite сохраняет исходный Host, поэтому проверка работает и при смене порта клиента. Ответы API имеют `Cache-Control: no-store`. Не следует включать CORS или менять proxy Host без пересмотра этой политики.

Клиент посылает `X-PlayFit-User` с ожидаемым ID для операций аккаунта. Сервер сравнивает его с владельцем cookie и при смене аккаунта в другой вкладке возвращает `409 ACCOUNT_CHANGED`; этот заголовок не является авторизацией. При focus/storage клиент перепроверяет вход. Смена ID размонтирует данные прежнего аккаунта и тренировку. Сбой проверки не переключает текущую страницу на другой источник. При недоступности сервера на первом открытии можно явно выбрать гостевой режим.

| Метод и путь | Тело / ответ |
| --- | --- |
| POST `/api/auth/register` | `{login,password}` → 201 `{user}` и cookie |
| POST `/api/auth/login` | `{login,password}` → `{user}` и новая cookie |
| GET `/api/auth/me` | `{user}` либо `{user:null}` |
| POST `/api/auth/logout` | `{}` → `{ok:true}`, идемпотентен |
| GET `/api/profile` | `{user,stats:{workouts,reps,seconds,demos}}` |
| PATCH `/api/profile` | `{nickname,avatar}` → `{user}` |

`user`: `{id,login,nickname,avatar,createdAt}`. Только собственный профиль; ID владельца в body/query не принимается. Никнейм 1–32 символа после удаления краевых пробелов, аватары `sprout/bolt/sun/mountain` — встроенные SVG. Статистика вычисляется из нескрытой истории: камера, видео и исторический импорт, демо отдельно. Время включает подготовку/отдых/паузы. XP и достижения реализованы отдельно по допустимым событиям: [правила этапа 5](game-rules.md). Статистика истории и прогрессия имеют разные подписанные источники.

## Запуски и результаты

POST `/api/runs` принимает `{requestId,exercise,mode,goal:{sets,reps,restSeconds},conditions}`. Проверяются два существующих упражнения и три источника; пределы цели прежние. Создаётся `{id,snapshot,createdAt}`. Уникальность `(user_id,request_id)` обеспечивает безопасный повтор после потери ответа; тот же ключ с другой целью → `409 RUN_CONFLICT`. Снимок и время сервера не изменяются. Клиент начинает анализ только после успешного создания запуска; сбой не запускает гостевое сохранение.

POST `/api/runs/:id/complete` принимает `{record:WorkoutRecordV1}`. `record.id` равен ID запуска, exercise/mode/goal/conditions точно совпадают со снимком. Доступ по владельцу обязателен. Сервер проверяет полную вложенную структуру, допустимые значения, соответствие счётчиков реальным исходам/замечаниям попыток, критерии упражнения, баланс наблюдений и длительностей. Неизвестные поля, в том числе видео/landmarks, отклоняются. Ограничения: 4 MiB, 5000 попыток суммарно, 100 подходов, длительность не более 7 суток. При превышении результат остаётся доступен на экране для экспорта, API не заявляет успех. JSON Schema на сервере дополняет общую проверку v1; браузерный парсер прежних записей не ужесточён.

Один результат на run ID, содержимое хранится в каноническом JSON с рекурсивной сортировкой ключей. Первый запрос → 201, равнозначный повтор → 200 с тем же результатом, изменённое содержимое → `409 RESULT_CONFLICT`. Клиент держит тот же run ID и результат при повторе, показывает ожидание/ошибку/подтверждение отдельно. После ухода или reload несохранённая тренировка в памяти теряется: экспортировать её нужно до ухода. Запуски без результата остаются в БД, но не входят в историю.

`AccountResult`: `{id,runId,source,sourceVersion,originalId,createdAt,archivedAt,record}`. ID результата отличается от ID запуска; ID внутри WorkoutRecord — ID запуска или исходной импортированной записи. Уникальный run и составной FK `(run_id,user_id)` защищают связь на уровне SQLite.

| Метод и путь | Поведение |
| --- | --- |
| GET `/api/history` | `{results:AccountResult[]}` только собственного аккаунта, без архивных |
| GET `/api/history/:id` | `{result}` собственного владельца, включая скрытый результат |
| DELETE `/api/history/:id` | идемпотентно устанавливает archivedAt; `{ok:true}` |

Чужой/отсутствующий объект → 404. Отдельного endpoint экспорта нет: UI экспортирует уже авторизованные результаты. Формат `{schemaVersion:1,records,accountResults}` сохраняет читаемый v1-конверт и серверное происхождение. В `records` для уникальности ID используются ID серверных результатов; исходный record ID дополнительно хранится в `accountResults.recordId`.

Архивирование скрывает запись из списка и прежних показателей истории, оставляя данные и связи. XP, достижения и активность этапа 5 сохраняются: скрытие не отменяет событие. Каскадного удаления нет. Прямые детали владельцу доступны; повтор завершения или импорта не снимает архивирование. В UI это действие называется «Скрыть», с объяснением и подтверждением. Гостевые записи по-прежнему удаляются только из localStorage по старым правилам.

## Исторический импорт

POST `/api/history/import/preview` и POST `/api/history/import` принимают `{schemaVersion:1,source:"playfit.workouts.v1",records:WorkoutRecordV1[]}`, от 1 до 20 записей, до 4 MiB. Оба возвращают `{added,existing,total}`; preview ничего не записывает. Проверки как для нового результата, но связь с новым запуском не создаётся. Сохранённый `source=historical_import`, `sourceVersion=1`, `originalId=record.id`, `runId=null`. Уникальность по пользователю/источнику/исходному ID, проверка содержимого, конфликт → 409 и откат всего запроса. Повторный импорт скрытой записи также считается уже выполненным.

UI читает localStorage только после нажатия «Посмотреть итог импорта», получает серверный итог по каждой записи и показывает аккаунт назначения, количество новых/прежних и режимы. После явного подтверждения переносит записи последовательно, безопасно повторяет после частичного сетевого сбоя. Каждый запрос транзакционен; весь большой UI-импорт не одна транзакция. Исходный снимок гостевых записей не удаляется и не изменяется. Для другого аккаунта preview и дедупликация выполняются заново.

Ни импорт, ни демо, ни видеофайлы не дают игровых наград. На этапе 5 награды опираются на сохранённые сервером события и допустимые новые камерные запуски, используя серверное время завершения и снимок. См. [game-rules.md](game-rules.md). Проверка подлинности движения или защита от подделки клиентского результата не заявляется.

## Ошибки и проверки

Сохранён формат `{error:{code,message,requestId}}` без SQL/паролей/стека. Дополнены коды `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `LOGIN_TAKEN`, `AUTH_RATE_LIMIT`, `ORIGIN_REJECTED`, `ACCOUNT_CHANGED`, `INVALID_RESULT`, `RUN_CONFLICT`, `SNAPSHOT_MISMATCH`, `RESULT_CONFLICT`, `IMPORT_CONFLICT`. Схемы не удаляют неизвестные поля и не приводят типы.

Тесты: `npm test`, `npm run test:server`, `npm run check:server`, `npm run build`. Серверные проверки используют временные файловые БД: два аккаунта, хеши/соли/сроки/выход/перезапуск, CSRF, владение, неверные агрегаты и вложенные поля, снимок цели, однократное завершение, preview/импорт/конфликт/откат/архивирование. Клиентские тесты моделируют потерю ответа и проверяют устойчивые request/run ID, ожидаемого владельца и передачу ошибок без смены источника.


Фактическая приёмка 20.10.2026: `npm test` — 180 тестов, 14 файлов (27 серверных); `npm run build` и `git diff --check` проходят. Собранный `npm run start:server` проверен на временной БД и порту 3102 по HTTP: health schemaVersion=2, регистрация 201, профиль и история 200. В IAB проверены регистрация/несовпадающие пароли/неверный вход/выход/повторный вход двух аккаунтов, сохранение профиля и аватара после reload, отдельная гостевая история, демо аккаунта, детали, явный импорт с preview и повтором без дубликатов, JSON-экспорт с успешным чтением v1-парсером. История Алисы осталась из 1 записи, импорт Боба — из 3, источники не смешались. Широкая и узкая компоновки измерены как 1440 и 390 CSS px, без горизонтального переполнения. Искусственный отказ INSERT во временной UI-БД показал ошибку сохранения; после снятия отказа тот же результат успешно сохранён повтором в единственном экземпляре. Чистое открытие после завершения изменений — без console error/warn. При горячем обновлении выявлена смена контекста React; контекст и Provider разделены, чистое открытие перепроверено. Камера, реальные видео, разрешения и точность распознавания людей не проверялись.
