# Бесплатный учебный показ: Render + Neon

Подготовлено 28.10.2026. Это инструкция для публикации; наличие файлов конфигурации не означает, что сайт уже размещён. Учётные записи и результаты размещённого приложения хранятся в PostgreSQL Neon. Видео, локальные видеофайлы, распознавание MediaPipe и поток точек остаются на устройстве посетителя.

## Схема и стоимость

Один **Web Service / Free** на Render запускает Fastify и раздаёт `dist/`. Один **Free**-проект Neon хранит PostgreSQL. Преподаватель открывает HTTPS-ссылку вида `https://имя.onrender.com`; собственный домен, GPU и внешние AI API не нужны.

Для небольшого учебного показа достаточно бесплатных квот. Выбирай именно Free в обоих сервисах, без платных ресурсов и постоянного диска Render. Это бесплатные планы с ограничениями, а не гарантия неограниченного хостинга: тарифы и квоты нужно сверить при регистрации. Render останавливает Free-сервис после 15 минут без трафика; первое открытие после паузы занимает примерно минуту. Сохранённые в Neon данные от этого не пропадают. Не используй бесплатный Render Postgres: его срок ограничен 30 днями.

Источники: [Render Free](https://render.com/docs/free), [Neon Free](https://neon.com/pricing), [Blueprint](https://render.com/docs/blueprint-spec), [переменные Render](https://render.com/docs/environment-variables).

## 1. Создать базу Neon

1. Зарегистрируйся в [Neon](https://console.neon.tech/) и создай проект на **Free**. Предпочтительно выбрать регион рядом с Render Frankfurt.
2. Открой **Connect**, выбери созданную базу и скопируй PostgreSQL connection string. Для этой небольшой платформы подходит обычное прямое подключение; пул соединений уже ограничен четырьмя на процесс приложения. Neon также поддерживает pooled URL: приложение использует транзакции и транзакционные advisory locks, без session-level locks.
3. Сохрани TLS: используй `sslmode=verify-full` (если Neon выдаёт `sslmode=require`, его также принимает приложение). Остальные параметры из Neon сохраняй. Не вставляй URL в исходники, `render.yaml`, скриншоты или публичный чат: он содержит пароль.

Новая облачная БД изначально пустая. Локальная SQLite не отправляется в Neon и не изменяется. Создай новые аккаунты для показа; гостевую историю можно импортировать существующей явной кнопкой приложения без игровых наград. Автоматического переноса локальных аккаунтов/паролей/сессий нет.

## 2. Развернуть приложение Render

Код должен находиться в GitHub-репозитории, к которому ты предоставишь доступ Render. Публикация/отправка кода и запуск облачного развёртывания — отдельные действия после подготовки проекта.

Через **New → Blueprint** выбери репозиторий и корневой `render.yaml`. Он создаёт только один бесплатный Web Service и просит секрет **DATABASE_URL**: вставь строку Neon. База Render и платный диск в Blueprint не создаются. Автоматические деплои отключены; дальнейшие обновления запускаются вручную.

Можно создать **New → Web Service** вручную с теми же настройками:

| Поле | Значение |
| --- | --- |
| Runtime | Node |
| Region | Frankfurt |
| Instance Type | **Free** |
| Root Directory | корень этого приложения, где находится `package.json` |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Auto-Deploy | Off |
| Environment: `NODE_VERSION` | `22` |
| Environment: `NODE_ENV` | `production` |
| Environment: `DATABASE_URL` | секретный URL Neon |

`PORT` и `RENDER_EXTERNAL_URL` выставляет Render. Приложение слушает `0.0.0.0:$PORT`, проверяет HTTPS origin по `RENDER_EXTERNAL_URL`, применяет миграции до открытия порта и затем обслуживает и клиент, и `/api`. Production-сессия имеет `HttpOnly`, `SameSite=Strict`, `Secure`; проверка origin не полагается на произвольный forwarded host. В production без PostgreSQL и HTTPS origin запуск отклоняется, чтобы аккаунты не попали во временную SQLite.

При собственном домене добавь `PUBLIC_ORIGIN=https://твой-домен` без завершающего `/` и пути. В таком случае использовать приложение нужно с этого домена. На стандартном `onrender.com` `PUBLIC_ORIGIN` не нужен.

## 3. При необходимости наполнить показ

Обычный запуск применяет только миграции и каталог программ. Он не создаёт вымышленных пользователей, результаты и награды. На Render Free shell недоступен; для явного наполнения можно временно изменить **Start Command**:

```sh
npm run db:seed:challenges:built && npm start
```

Для явно помеченного учебного рейтинга с 12 вымышленными участниками:

```sh
npm run db:seed:challenges:built && npm run db:seed:demo:built && npm start
```

Выполни ручной deploy. После успешного наполнения верни **Start Command** к `npm start` и снова разверни сервис. Команды повторяемы: не удаляют аккаунты/результаты, не начисляют повторные награды и не меняют принятые условия. Наборы привязаны к неделе Europe/Kyiv; перед показом в другую неделю наполнение можно повторить. Миграции и seed работают с БД из `DATABASE_URL`, а не с локальной SQLite.

Обычный рейтинг — `/leaderboard`, вымышленные участники — `/leaderboard?mode=demo`. Учебные логины `demo_01`–`demo_12`, пароль `PlayFitStudy2026`: он публичный и относится только к помеченным демонстрационным аккаунтам. Для личных данных создай отдельный обычный аккаунт. Синтетическое демо тренировки не начисляет наград; демонстрационное наполнение рейтинга — отдельный явный сценарий. Подробнее: [учебный показ](demo.md).

## 4. Проверить ссылку перед отправкой преподавателю

1. Открыть `/api/health`: должен вернуться JSON со `status: "ok"`, `database: "ok"`, `schemaVersion: 10`.
2. Открыть сайт, зарегистрироваться, выйти и войти снова. Обновить `/overview` и `/programs/squat-pushup` напрямую: страницы должны открываться.
3. Попробовать синтетическое демо без камеры и проверить сохранение результата. Для камеры разрешить доступ браузеру по HTTPS. Точность распознавания на людях этим не подтверждается.
4. Открыть сайт в другом браузере/приватном окне: история аккаунта появляется только после входа в тот же аккаунт; гостевая история остаётся в своём браузере.
5. После ручного перезапуска Render снова войти и проверить, что данные сохранились. Перед показом открыть сайт заранее и дождаться пробуждения Free-сервиса.

## Локальный запуск и проверки

Прежний локальный режим с SQLite:

```sh
npm ci
npm run db:migrate
npm run dev
```

Проверка собранного клиента и API одним процессом с локальной SQLite:

```sh
npm run build
npm start
```

Открыть `http://127.0.0.1:3001`. Если задан `PORT` или `API_PORT`, использовать его. `NODE_ENV=production` для этого локального SQLite-сценария не выставлять. `npm run start:server` по-прежнему запускает API для совместной работы с Vite/preview.

Для локального PostgreSQL можно задать `DATABASE_URL` в игнорируемом `.env`, затем использовать те же migrate/seed/dev-команды. При наличии URL SQLite не открывается. Реальные секреты не должны иметь префикса `VITE_`.

```sh
npm test
npm run build
npm run test:postgres
```

Последней команде нужен `TEST_DATABASE_URL` на отдельную тестовую PostgreSQL-базу с правом `CREATE SCHEMA`. Она создаёт случайные `playfit_test_*` схемы и удаляет только их; без URL PostgreSQL-тесты пропускаются. Не используй для них production-базу. Обычные серверные тесты используют временную SQLite. Тестовые результаты тренировок искусственные.

## Контракты хранения и миграций

- `server/store.ts`: асинхронные параметризованные запросы, закреплённое соединение транзакции через AsyncLocalStorage, вложенные savepoint, пул до 4 соединений. SQLite остаётся локальным драйвером; обращения к одному файлу сериализуются без блокировки event loop при ожидании чужой транзакции.
- PostgreSQL-транзакции берут общий `pg_advisory_xact_lock` до чтения состояния. Для малой учебной платформы это намеренно сериализует изменения программ, идемпотентные сохранения, ограничения XP, принятие/завершение дуэлей и миграции между процессами. Это не архитектура для высокой нагрузки.
- Исходные `server/migrations/001_…010_*.sql` не изменены. PostgreSQL имеет собственные отслеживаемые `server/migrations/postgres/001_…010_*.sql`, таблицы, FK, ограничения и защитные триггеры. Выбор каталога автоматический по драйверу. Все ожидающие миграции и их checksum-журнал применяются одной транзакцией. Изменение уже применённого SQL останавливает запуск. Версии и история в SQLite не переписываются.
- API и JSON-контракты результатов прежние; даты хранятся ISO UTC, календарь наград — Europe/Kyiv. SQLite `rowid` заменён явными стабильными сортировками по идентификатору/дате. `COUNT/SUM/RANK` PostgreSQL преобразуются в безопасные целые числа, camelCase alias сохранены.
- Сервер раздаёт только `dist/`: HTML с `no-cache`, хешированные assets с долгим immutable-кешем, модель/WASM/звук с обычным кешем. SPA fallback не подменяет неизвестные `/api` и отсутствующие файлы; `.env`, серверные исходники и SQLite вне каталога раздачи.

Тесты на PostgreSQL и локальный HTTP-показ не заменяют проверку конечной HTTPS-ссылки в реальных аккаунтах Render/Neon. После фактической публикации нужно выполнить пункт 4.

## Выполненные проверки подготовки

28.10.2026: `npm test` с `TEST_DATABASE_URL` — **390 тестов / 31 файл**, включая 5 интеграционных тестов на настоящем PostgreSQL 17. Проверены совпадение каталога/снимков SQLite и PostgreSQL, повтор миграций без потери строк, откат ошибочного SQL, сохранение сессий между подключениями, изоляция аккаунтов, одновременные повторы запуска/завершения, дневной предел XP, отсутствие наград за демо/импорт, личные версии программ, испытание, дуэль, рейтинг и идемпотентное демонстрационное наполнение. Искусственный сбой PostgreSQL-триггера откатывает результат, события и награды целиком; повтор затем успешен.

`npm run build`, `npm run check:server`, `git diff --check` успешны. `npm audit --omit=dev` не обнаружил уязвимостей в runtime-зависимостях. Vite выдаёт предупреждение о размере основного JS-чанка; сборка завершается успешно.

Собранный `npm start` проверен по настоящему HTTP с отдельной временной PostgreSQL-базой. В браузере пройдены регистрация, обзор с пустыми данными, reload с сохранённой сессией, синтетическая тренировка 1×1, подтверждённое серверное сохранение без XP, история и прямая ссылка на результат. Просмотрены широкая компоновка 1440×900 и узкая 390×844; консоль браузера без предупреждений и ошибок. Камера и распознавание на людях не проверялись. Локальные тестовые сервер и база отделены от пользовательской SQLite; внешние Render/Neon не создавались и не изменялись.
